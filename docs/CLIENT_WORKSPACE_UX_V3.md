# OLYA AI — клиентский ЛК / Chat UX v3

## Цель

Клиентский интерфейс должен ощущаться как спокойный AI-чат, а не как панель управления инфраструктурой. Основная задача экрана `/app` — написать запрос, получить ответ, остановить генерацию при необходимости, приложить файл, выбрать понятную мощность ответа и без потери позиции читать длинный диалог.

Главный принцип: **чат — основной продукт, настройки вторичны**. Пользователь не должен видеть технические параметры модели, очереди и телеметрию, пока они не нужны для решения задачи.

## 1. Каркас экрана

### Desktop

Экран занимает ровно доступную высоту браузера (`100dvh` / `visualViewport.height`) и сам документ не прокручивается.

Структура:

1. Левая боковая панель — 260 px.
2. Основная область — остаток ширины.
3. В основной области сверху находится минимальная служебная полоса.
4. Центр занимает **единственный прокручиваемый контейнер сообщений**.
5. Composer является отдельным нижним flex-блоком, не входит в scroll сообщений и никогда не уезжает вниз вместе с историей.

Важный технический контракт: на всех уровнях `shell -> main -> view-chat -> messages` должны корректно стоять `min-height:0`; `body` не имеет собственного scroll.

### Mobile

- Высота берётся из `window.visualViewport.height`, если API доступен. Это предотвращает прыжок composer при открытии клавиатуры.
- Sidebar становится off-canvas панелью шириной до 290 px.
- За sidebar появляется отдельный затемняющий overlay; тап по overlay закрывает меню.
- Composer учитывает `safe-area-inset-bottom`.
- Максимальная высота textarea ограничена примерно 35% видимой высоты, чтобы пользователь всегда видел часть диалога.

## 2. Левая панель

Порядок сверху вниз:

1. `OLYA AI`.
2. Кнопка `Новый чат`.
3. Основные пользовательские разделы: `Чат`, `Проекты`, `Изображения`.
4. Недавние диалоги — прокручиваются независимо.
5. Внизу — аккаунт/выход и доступ к поддержке.

### Что не показываем в основном меню

- `Файлы` — файлы прикрепляются через `+` прямо в чате.
- `API` — профессиональная функция остаётся доступной из аккаунта / API Console, но не конкурирует с чатом в основной навигации.
- Технические статусы модели.

## 3. Область сообщений

### Поведение прокрутки

Это отдельный `overflow-y:auto` контейнер.

Правила:

1. Если пользователь находится около нижней границы, streaming автоматически следует за новым текстом.
2. Если пользователь прокрутил вверх, приложение **перестаёт тянуть его вниз** при каждом токене.
3. В этом состоянии появляется компактная плавающая кнопка `↓` — перейти к последнему сообщению.
4. Нажатие на `↓` возвращает auto-follow.
5. Отправка нового собственного сообщения снова включает auto-follow.
6. Загрузка старой истории сверху не должна неожиданно переносить пользователя вниз.

### Сообщение пользователя

- Справа.
- Нейтральный светло-серый bubble.
- Максимальная ширина ограничена, длинные слова не ломают layout.

### Ответ OLYA AI

- Не помещается в тяжёлую карточку; текст находится на основном белом фоне.
- Максимальная ширина текста около 800 px.
- Markdown, таблицы и код имеют горизонтальный overflow внутри себя, а не расширяют весь экран.
- Источники и ссылки на файлы свернуты по умолчанию.
- Технические badges `TTFT`, `tokens/sec`, внутренний mode, quality telemetry скрыты от обычного пользователя.

### Ошибки

Ошибка показывается рядом с местом ответа. `Повторить` выводится только когда повтор действительно возможен. Интерфейс не очищает пользовательский запрос после транспортной ошибки без возможности восстановления.

## 4. Пустой чат

В центре:

- Заголовок `Чем могу помочь?`.
- Несколько коротких примеров запросов. Они должны заполнять textarea, но не отправлять запрос автоматически.

На маленьком экране подсказки сокращаются до минимального количества, чтобы composer оставался главным элементом.

## 5. Composer

Composer всегда находится внизу и визуально является главным интерактивным блоком.

### Верхняя часть composer

- Auto-growing textarea.
- Enter — отправка.
- Shift+Enter — новая строка.
- Высота textarea ограничена; после достижения лимита прокручивается сама textarea, а не весь экран.

### Нижняя строка

Слева направо:

1. `+` — прикрепить файл.
2. Выбор мощности: `Простая / Средняя / Сложная`.
3. `⋯` — редкие дополнительные настройки.
4. Справа круглая кнопка `↑`.

Во время генерации кнопка `↑` превращается в `■` и вызывает существующий cancel endpoint. Не создаётся отдельная большая кнопка `Остановить`, поэтому геометрия composer не меняется.

### Мощность

Пользователь не видит внутренние названия Fast/Work/Deep.

- **Простая** → backend `auto`. Это не старый Fast: сервер сам выбирает минимум Work и при необходимости Deep.
- **Средняя** → backend `work`.
- **Сложная** → backend `deep`, reasoning включён.

Это даёт понятную модель выбора без технической терминологии.

### Меню `⋯`

Содержит только вторичные опции:

- Проект / контекст.
- Интернет: авто / всегда / выключен.
- Проверка ответа: авто / строгая / выключена.

Меню открывается вверх от composer и закрывается кликом вне него или `Escape`.

## 6. Файлы

Отдельный раздел файлов не является частью пользовательской навигации.

Основной сценарий:

1. Пользователь нажимает `+`.
2. Выбирает файл.
3. Если выбран проект, файл загружается в его контекст через текущий project-file API.
4. Пользователь видит короткий статус загрузки возле composer.
5. После готовности сразу может задать вопрос по документу.

До появления conversation-scoped storage файл без проекта не должен молча теряться или индексироваться в неизвестный контекст: интерфейс явно просит выбрать проект.

## 7. Статус выполнения

Многочисленные progress pills (`queued/researching/thinking/generating/verifying`) не должны менять высоту страницы и отвлекать пользователя.

В обычном интерфейсе используется одна стабильная строка статуса внутри composer:

- `Готовлю ответ…`
- `Ищу актуальные источники…`
- `Проверяю ответ…`
- сообщения об ошибке.

Технические этапы остаются в DOM/API для диагностики, но не формируют отдельную прыгающую панель.

## 8. Стабильность

### Нельзя

- прокручивать `body` вместо `messages`;
- менять высоту нижней панели при каждом статусе;
- принудительно скроллить вниз, когда пользователь читает старый текст;
- расширять layout длинным кодом, URL или таблицей;
- позволять double-submit во время активной генерации;
- терять кнопку stop при streaming;
- прятать cancel за меню;
- использовать hover как единственный способ получить критическое действие.

### Обязательно

- `overscroll-behavior: contain` для сообщений;
- `scrollbar-gutter: stable` на desktop;
- `prefers-reduced-motion`;
- понятный focus-visible;
- минимум 44 px hit-area на mobile для основных кнопок;
- safe-area на iOS/Android;
- отсутствие layout shift при переключении `↑` ↔ `■`.

## 9. Симулированные пользовательские проходы

Это UX-walkthrough, а не реальное исследование с живыми респондентами.

### Пользователь 1 — обычный человек

Сценарий: открыть ЛК → задать вопрос → получить ответ → задать уточнение.

Риск старого UI: непонятные Fast/Work/Deep, verify, web, project одновременно перед глазами.

Решение: оставить `+`, мощность и `⋯`; остальные параметры спрятать.

### Пользователь 2 — читает длинный ответ

Сценарий: во время streaming прокрутить вверх и сверить предыдущий абзац.

Риск: постоянный автоскролл возвращает вниз.

Решение: near-bottom tracking + отключение auto-follow + кнопка `↓`.

### Пользователь 3 — передумал

Сценарий: отправить сложный запрос и через секунду остановить.

Риск: stop меняет размеры/место или скрыт.

Решение: та же круглая кнопка справа; только glyph меняется `↑ -> ■`.

### Пользователь 4 — телефон

Сценарий: открыть клавиатуру и написать длинный промпт.

Риск: `100vh` и экранная клавиатура сдвигают composer за viewport.

Решение: `visualViewport.height`, `100dvh`, safe-area и ограничение высоты textarea.

### Пользователь 5 — работа с файлом

Сценарий: прикрепить документ и сразу спросить по нему.

Риск: отдельный раздел `Файлы` разрывает основной flow.

Решение: загрузка через `+` в composer.

### Пользователь 6 — power user

Сценарий: включить интернет всегда, строгую проверку, выбрать проект.

Риск: скрыть возможности слишком глубоко.

Решение: единая кнопка `⋯` рядом с мощностью; всё доступно максимум за один дополнительный клик.

## 10. Acceptance criteria

1. `/app` не имеет body-scroll при активном чате.
2. Composer остаётся видимым при длинной истории.
3. Mobile keyboard не выбрасывает composer за экран.
4. Пользователь может остановить активную генерацию одной кнопкой.
5. Во время streaming пользователь может читать историю без принудительного возврата вниз.
6. В основном интерфейсе нет Fast/Work/Deep, TTFT/tps и отдельной кнопки файлов.
7. Есть ровно три понятных уровня мощности: Простая / Средняя / Сложная.
8. Редкие настройки спрятаны под `⋯`.
9. Код, таблицы и URL не ломают ширину чата.
10. Все изменения сохраняют текущие backend endpoints и существующие механизмы cancel/recovery/files/projects.
