# OLYA AI: симуляция 10 000 реальных пользовательских сессий

## Зачем

Контур ловит ошибки, которые не видны на «идеальных» тестовых вопросах: разговорные формулировки, вежливые вводные, мобильный ввод без пунктуации, emoji, короткие follow-up, память, свежие данные, локальный поиск, регулируемые правила, длинные тексты и профессиональные задачи.

Главная цель — одновременно улучшать корректность маршрутизации, качество ответа и latency, не превращая каждый запрос в web-search или несколько LLM-проходов.

## Панель

Панель содержит ровно 10 000 синтетических сессий:

- 100 канонических пользовательских задач;
- 20 персон: обычный пользователь, домохозяйка/родитель, подросток, школьник, студенты, пожилой пользователь, офисный сотрудник, предприниматель, маркетолог, SMM, SEO, разработчик, системный администратор, дизайнер, фрилансер, продавец маркетплейса, HR, бухгалтер, путешественник;
- 5 способов формулировки: exact, polite, mobile, colloquial, noisy.

Часть канонических слотов заменяется профильными задачами конкретной персоны. Поэтому профессия и возраст — реальные измерения теста, а не подписи над одинаковыми вопросами.

## Что проверяется на всех 10 000

`scripts/real_user_routing_audit_10000.py` прогоняет всю панель через production-классификаторы и проверяет ожидаемый путь:

- instant utility: приветствие, арифметика, единицы, время и быстрые уточнения;
- structured facts: погода, валюты, ключевая ставка, криптовалюты, местное время;
- atomic knowledge: короткие стабильные факты без web;
- direct: обычные объяснения и самодостаточные writing-задачи;
- web: текущие роли, версии, покупки, локальные места, регулируемые правила, налоги и рекомендации, где свежесть важна;
- context и memory;
- explicit long-form.

Дополнительные hard-edge проверки защищают от регрессий вроде:

- `Подскажи, пожалуйста, сколько будет 17 * 23? 🙏` -> calculator;
- `Где поесть рядом?` -> мгновенное уточнение локации;
- `Где поесть рядом с Красной площадью в Москве?` -> fresh web;
- `Как работает УСН?` -> fresh web;
- `Что такое НДС?` -> stable atomic explanation;
- rewrite текста со словами `лучшие рекомендации`, `рейтинг`, `отзывы` -> direct без лишнего web.

Статический 10k-аудит входит в deploy release-gate и должен иметь 0 route mismatch и 0 hard-edge failure.

## Live-тест сайта и нейросети

`scripts/real_user_live_weighted_10000.py` запускает настоящие HTTP/SSE-сессии через приложение. Для теста создаются изолированные временные пользователи, которые после прогона удаляются. На один аккаунт приходится существенно меньше production abuse-breaker threshold.

Дорогая live-выборка usage-weighted: больше типичных запросов на информацию, практические рекомендации и письмо, но сохраняется покрытие программистов, бизнеса, памяти, контекста и всех пяти стилей ввода.

Полные 10 000 live-генераций поддерживаются через `--full`, но на одном CPU inference-slot это endurance/load test, а не разумный ежедневный quality test.

## Что оценивается в live-ответе

Базовые проверки:

- транспорт/runtime;
- пустой, слишком короткий или слишком длинный ответ;
- обязательные факты для контрольных сценариев;
- память и контекст;
- правильное использование web и наличие источников;
- чтение страниц для research/advice;
- vendor/model leaks;
- неожиданные китайские иероглифы в русском ответе;
- лишний critic/repair LLM-pass;
- prompt bloat;
- непроверенные URL.

`answer_quality_lint.py` дополнительно ловит:

- `<think>` и внутренние role/control tokens;
- ненужное `как ИИ/языковая модель`;
- языковой mismatch;
- незакрытые code fences;
- повторяющиеся предложения и repetition loops;
- echo пользовательского запроса;
- вероятно оборванный ответ.

Эти дефекты уменьшают pass-rate, а не просто записываются в журнал.

## Метрики скорости

Live-report разделяет:

- client TTFT — когда пользователь реально увидел первый текст;
- server TTFT — latency внутри answer pipeline/model;
- queue_ms — ожидание inference slot;
- stream overhead — разница client/server TTFT;
- tokens/sec;
- полное время ответа;
- quality score.

В отчёте считаются p50/p95/p99 latency, p10/p50 tokens/sec и quality, а также срезы по category/persona/style. Это позволяет отличить медленную модель от очереди, web, SSE/UI или раздутого контекста.

## Запуск

После обновления production:

```bash
cd /opt/olya-ai
git pull origin main
bash scripts/deploy_client_product_refresh.sh
```

Deploy сначала компилирует изменённые модули, затем запускает latency-regression и полный 10 000 routing audit.

Рекомендуемый первый live-прогон:

```bash
bash scripts/run_real_user_simulation_10000.sh --limit 200 --longform-limit 2
```

Расширенный quality-прогон:

```bash
bash scripts/run_real_user_simulation_10000.sh --limit 500 --longform-limit 5
```

Полный endurance-test всех 10 000 live-сессий:

```bash
bash scripts/run_real_user_simulation_10000.sh --full
```

JSON и Markdown отчёты live-теста сохраняются в `/tmp/olya-real-user-10000-*.json` и `/tmp/olya-real-user-10000-*.md`.

## Правило оптимизации

Не снижать hard token caps и не добавлять второй LLM-pass «на глаз». Сначала смотреть распределения output_tokens, TTFT, queue_ms, tokens/sec, quality failures и категории запросов. Оптимизация считается успешной только если latency уменьшается без ухудшения pass-rate и quality score.
